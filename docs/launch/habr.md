# Хабр: черновик статьи

**Заголовок:** ИИ-агент написал тест к своему фиксу. Мы проверили, падает ли этот тест без фикса

**Хабы:** Тестирование IT-систем, Python, JavaScript, Искусственный интеллект, Open source

---

Агенты вроде Claude Code, Codex и Copilot научились делать pull request, который выглядит готовым: фикс есть, тест добавлен, CI зелёный. Но зелёный CI говорит только одно: тесты проходят. Он не говорит, поймал бы этот тест баг, если бы фикса не было.

Проверить это просто: откатить исправление и запустить тест ещё раз. Если тест всё равно проходит, он ничего не доказывает. Многие команды делают это руками, а некоторые уже пишут для этого скрипты: `verify-red` в CI, галочки «Red→Green» в шаблонах PR для кода от ИИ.

Мы сделали из этого инструмент — Receipts — и прогнали его на реальной истории open source.

## Что делает Receipts

1. Находит в PR тесты, которые добавлены или изменены: функции pytest, блоки `it`/`test` в vitest и jest, включая строки в таблицах `@pytest.mark.parametrize` и `.each`.
2. Запускает их с изменением.
3. Откатывает к базовой ветке только изменённые файлы кода. Тесты, зависимости и конфиги остаются новыми.
4. Запускает тесты ещё раз и выносит вердикт по каждому.

| Вердикт | Смысл |
|---|---|
| ✅ PROVEN | Падает без изменения и проходит с ним: тест доказывает фикс |
| 🛡️ GUARD | Проходит в обоих случаях, но рядом есть доказывающий тест: охраняет старое поведение |
| ⚠️ THEATER | Проходит в обоих случаях, и ни один тест не доказывает изменение |
| 🟡 WEAK | Падает без изменения только потому, что вызываемой функции ещё не было |
| ❌ BROKEN / 🔁 FLAKY | Падает с изменением / нестабилен |

Никакой LLM: результат детерминированный и получается прогоном ваших тестов. Код никуда не уходит.

## Что показали цифры

Мы взяли 181 изменений из 17 репозиториев:
- коммиты-фиксы мейнтейнеров в click, sqlparse, marshmallow, dateutil, dayjs и ещё семи библиотеках;
- 100 PR с отпечатками агентов (в основном Claude Code, а также Codex, Cursor, Copilot) в claude-agent-sdk-python, openai-agents-python, MCP Python SDK, fastmcp и simonw/llm.

| | Изменений | Оценено | Доказано | Частично | Не доказано | Только WEAK |
|---|---|---|---|---|---|---|
| Фиксы мейнтейнеров | 81 | 71 | 64 (90%) | 2 (3%) | 5 (7%) | 0 |
| PR агентов | 100 | 91 | 75 (82%) | 5 (5%) | 2 (2%) | 9 (10%) |

Проценты считаются от оценённых изменений. Остальные оценить не удалось: ни один тест не дал результата с обеих сторон, чаще всего из-за окружения.

Выводы:

- **Большинство изменений доказаны.** У мейнтейнеров 90%, у агентов 82% изменений доказаны: хотя бы один тест падает без изменения, и нет ни THEATER, ни WEAK. Это хорошо поставленные проекты, и тесты в них в основном работают.
- **Характерная слабость агентов не THEATER, а WEAK.** В 10% агентских PR тесты «падают» на старом коде только потому, что тестовый файл импортирует имя, которое добавляет фикс. На старом коде такой файл даже не загружается, поэтому старое поведение не проверяет ни один тест. У мейнтейнеров такого не встретилось ни разу.
- **Каждый THEATER — отдельная история.** Фиксы, меняющие только типы: новый ключ в `TypedDict` проходит тест и на старом коде, потому что Python не проверяет `TypedDict` во время выполнения. Фикс под Windows, проверенный на Linux. Фикс «мёртвого» `__repr__` в dateutil, где новый вывод совпал со стандартным, так что регрессионный тест прошёл бы и без фикса.

Методика, оговорки, все изменения со ссылками и скрипты для воспроизведения: https://github.com/syntaxixr/receipts/blob/main/docs/study.md

## Грабли, на которые мы наступили

**Регрессионный тест рядом с фиксом — это нормально.** Первая версия помечала как THEATER тесты, которые специально проверяют соседний случай («не сломали ли мы `schema.name`, пока чинили `BETWEEN .03`»). Такой тест обязан проходить в обоих случаях. Теперь это GUARD, и он не роняет проверку, если рядом есть PROVEN.

**Новый случай — это строка в таблице.** Чаще всего регрессионный тест в Python добавляют не новой функцией, а строкой в многострочный `@pytest.mark.parametrize`. Локатор должен считать декоратор частью теста.

**Окружение.** Фиксы часовых поясов в dayjs не воспроизводятся в UTC: их тесты гоняют с `TZ=America/New_York`. Receipts запускает раннер напрямую, поэтому окружение, от которого зависят тесты, нужно задавать на шаге CI.

**Установка не в editable-режиме.** Если проект поставлен через `pip install .`, тесты импортируют копию из site-packages, и откат файлов до них не доходит: все тесты «проходят в обоих случаях». Мы наступили на это сами в исследовании. Теперь Receipts смотрит, откуда реально загружен изменённый модуль, и вместо ложного THEATER пишет предупреждение.

**Зависание — тоже провал.** Частый фикс — от зависания. На старом коде тест висит вечно, поэтому Receipts убивает прогон по таймауту и засчитывает зависший тест как упавший, то есть PROVEN.

**Откат прямо в рабочей папке.** Отдельный git worktree ломает editable-установки (`pip install -e .`): пакет продолжает импортироваться из исходной папки. Поэтому Receipts подменяет файлы на месте, а каждый исходный байт сначала сохраняет в журнал в `.git`. Ctrl-C и `receipts restore` всё возвращают.

**Кэш байткода.** Если исправление той же длины сделано в ту же секунду, Python может взять `.pyc` от другой версии. Каждый прогон получает свой `PYTHONPYCACHEPREFIX`.

## Как попробовать

GitHub Action:

```yaml
- uses: actions/checkout@v4
  with: { fetch-depth: 0 }
# ... установка зависимостей проекта ...
- uses: syntaxixr/receipts@main
```

Для Claude Code есть плагин (`/plugin marketplace add syntaxixr/receipts`, затем `/plugin install receipts-check@receipts`), а для Codex, Cursor и других агентов тот же skill ставится через `npx skills add syntaxixr/receipts`. Skill учит агента доказывать свой фикс, прежде чем сказать «готово». В нашем прогоне Claude получил THEATER на своём тесте, сам заменил его тестом на 1900 год и получил PROVEN, не трогая сам фикс. Есть и Stop-хук, который делает это автоматически. Он запускает тесты репозитория, поэтому по умолчанию выключен и включается командой `git config receipts.hook true` только там, где вы доверяете коду.

Репозиторий, данные исследования и скрипты для воспроизведения: https://github.com/syntaxixr/receipts

Буду рад примерам, где вердикт неверен для вашего проекта.
